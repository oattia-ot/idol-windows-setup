Sizing & performance (S / M / L) hardware · cache · threads · memory Official min + 1M-file reference · validate with your corpus

S Small

Evaluation / PoC · ≤ ~100k–250k docs
1 node · 4–8 cores · 16–32 GB RAM
  • 200–500 GB total disk (OS + index + logs)
  • Official min scaled up: 2c / 4 GB / 100 GB
  • Tutorials: ~4 cores / 8 GB / 50 GB free
  • Single-host installer (this toolkit)

Lab, demos, first-time installs on laptop or small VM.

M Medium

Production · ~0.5M–1M docs
1–2 nodes · 8–16 cores · 32–64 GB RAM
  • Index volume ≈ 200–400 GB + OS / logs / apps
  • Separate NiFi flow / content / DB volumes
  • Prefer multiple smaller Content engines under load
  • Keep process memory inside physical RAM

Default for modest production before full 3-tier scale-out.

L Large

≈ 1M files (no sectioning / mirroring)
3 servers · 16 cores · 64 GB RAM each
  • Index: OS 250 · Index 400 · Logs 100 · App 100 GB
  • NiFi: OS 250 + 6×200 GB repos (~1.45 TB)
  • Processing: OS 250 · Logs 200 · Apps 400 · Backup 100
  • Content · Community · DAH · View · License · CFS · Find

Validated MoD-style layout. Multi-node outside this single-host toolkit.

S Small

PoC / light load
Default toolkit values are usually enough
  • IndexCacheMaxSize = 102400–204800 (100–200 MB)
  • DelayedSync = True
  • MaxSyncDelay = 120–300 s
[IndexCache] IndexCacheMaxSize=102400

Raise only if index log shows frequent “cache is full”.

M Medium

Steady-state · concurrent queries + incremental index
  • IndexCacheMaxSize = 204800–512000 (200–500 MB)
  • DelayedSync = True
  • MaxSyncDelay = 300–600 s
[Server] DelayedSync=True MaxSyncDelay=300 [IndexCache] IndexCacheMaxSize=307200

Balance indexing throughput and query freshness.

L Large / Bulk

1M-file bulk load on 64 GB Index Server
  • Bulk: 1–2 GB cache · MaxSyncDelay 900–1800
  • After load: shrink to 300–500 MB
  • Dynamic resize: DRERESIZEINDEXCACHE
  • Force flush: action=DRESYNC
IndexCacheMaxSize=1572864 MaxSyncDelay=1200

Large infrequent flushes beat many small ones.

S Small

Single-host lab
  • Content Threads = 4 (toolkit default)
  • Leave default index-thread behaviour
  • DAH not required for single Content

Enough for PoC and light concurrent queries.

M Medium

8–16 core hosts
  • Content Threads = 6–8
  • Match cores; leave headroom for OS + other services
  • DAH threads ≈ child Content threads (non-mirror)
[Server] Threads=8 DelayedSync=True

Query threads matter more than index threads unless many feeders.

L Large

16-core Index Server shared with Community/DAH/View
  • Content Threads = 8–12
  • Mirror-mode DAH threads = sum of child Content threads
  • Do not oversubscribe when co-located
  • Prefer multiple Content children under high QPS

Test thread counts; more is not always faster under I/O saturation.

S Small

Basic checks
  • action=MemoryReport after install & sample load
  • Confirm process fits in RAM
  • Watch free physical memory
curl "http://host:9100/action=MemoryReport"

Admin role required for MemoryReport.

M Medium

Ongoing monitoring
  • Track procresident_kb trend
  • Index Cache vs configured MaxSize
  • Numeric / Parametric field memory spikes
  • Map field IDs: GetTagNames&FieldType=numeric
action=MemoryReport&SystemMemory=False

Pair with GetStatus / IndexerGetStatus and IDOL Admin Memory tabs.

L Large

1M-file Index Server · 64 GB RAM
  • Baseline before bulk → during → after
  • Keep Content well under ~40–45 GB resident
  • After bulk: shrink cache, re-check MemoryReport
  • NodeTable scales with doc count — expect growth

Unexpected numeric memory → wrong field typing or noisy test data.

Sources: OpenText KD System Requirements (min 2 CPU / 4 GB / 100 GB), Size & Scale Content, Index Cache / Flush Process guidance, MemoryReport expert topic, and validated 1M-file hardware reference (16c / 64 GB × 3 nodes). Always measure with your corpus; multi-million or high-QPS designs need OpenText review.
